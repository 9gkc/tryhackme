## الملخص التنفيذي

تدور الغرفة حول منصة مراسلة باسم **Speed Chatter** أُطلقت بسرعة قبل عيد الحب، وتحتوي على وظيفة رفع صورة الملف الشخصي. يكشف الاستطلاع أن التطبيق يعمل عبر Flask وWerkzeug، وأن نقطة رفع الصورة تقبل امتدادات وملفات لا ينبغي قبولها.[1] [2]

لا يؤدي رفع ملف PHP إلى تنفيذ أوامر لأن الخادم مبني على Python ويعرض الملف كمحتوى ثابت، لكن قبول ملف Python يفتح مساراً أخطر عندما يعالجه التطبيق في سياق التنفيذ. برفع Python reverse shell ثم تشغيله عبر مسار معالجة الصورة، أمكن الحصول على shell عكسي بصلاحيات `root` وقراءة `flag.txt`.[2]

## مسار الحل

### 1. تحديد الخدمة وسطح الهجوم

بعد تشغيل Lab machine، يُستخدم العنوان الذي تعرضه TryHackMe للوصول إلى التطبيق على المنفذ `5000`:

```text
http://MACHINE_IP:5000/
```

يُجرى فحص الخدمات داخل نطاق الهدف المخصص للغرفة فقط:

```bash
nmap -p- -sV MACHINE_IP
```

يظهر منفذ SSH على `22`، وتظهر خدمة الويب على `5000` مع مؤشرات إلى Werkzeug/Python. يحدد ذلك طبيعة الملفات التي يمكن أن ينفذها التطبيق، ويجعل فحص نقاط رفع الملفات أكثر أولوية من تجربة web shells مخصصة لـ PHP.[2]

### 2. مراجعة وظائف Speed Chatter

تعرض الواجهة حساب المستخدم، وملفاً شخصياً، وغرفة محادثة، ووظيفة لتحديث صورة الملف الشخصي. كما تظهر في الواجهة طلبات خاصة بالرسائل مثل:

```text
GET  /api/messages
POST /api/send_message
POST /upload_profile_pic
```

يُستخدم `textContent` لعرض محتوى الرسائل بدلاً من `innerHTML`، لذلك لا يكون stored XSS مساراً عملياً هنا. أما رفع صورة الملف الشخصي فيقبل ملفاً يرسله المستخدم ويخزنه تحت مسار من نمط `/uploads/`، ما يجعله نقطة الاختبار الأهم.[2]

| الملاحظة | الدلالة الأمنية |
|---|---|
| التطبيق مبني على Flask/Werkzeug | ملفات PHP لن تُنفذ باعتبارها كوداً من الخادم |
| نقطة الرفع تقبل امتدادات غير مقيدة | احتمال تخزين ملفات قابلة للاستغلال |
| الملف المرفوع يظهر في مسار `/uploads/` | يمكن اختبار طريقة التخزين وطريقة المعالجة اللاحقة |
| المحادثة تعرض النص عبر `textContent` | يقل احتمال نجاح حقن HTML/JavaScript المخزن |

### 3. التحقق من سلوك رفع الملفات

يُرسل ملف اختبار عبر طلب `multipart/form-data` إلى نقطة رفع صورة الملف الشخصي:

```http
POST /upload_profile_pic HTTP/1.1
Content-Type: multipart/form-data; boundary=...
```

يُقبل الملف ويُعاد مساره تحت `/uploads/`، لكن رفع ملف PHP لا يؤدي إلى shell؛ فعند طلبه يعرضه الخادم كمحتوى ثابت، وبـ `Content-Type` من نمط `application/octet-stream`. هذه النتيجة متوقعة في تطبيق Flask، وتوضح أن نجاح الرفع وحده لا يعني أن الملف سيُنفذ.[2]

تُستبعد كذلك محاولات path traversal وSSTI وحقن JSON ضمن الحقول المتاحة عندما لا تنتج تنفيذاً أو قراءة غير مصرح بها. القرار الصحيح هو مطابقة الحمولة مع لغة الخادم ومسار المعالجة الفعلي، لا الاستمرار في استخدام payload مخصص لمنصة مختلفة.

### 4. استغلال الرفع غير المقيد بملف Python

بما أن التطبيق يعمل في بيئة Python، يُجهز Python reverse shell لتتصل بالعنوان والـ port الخاصين بـ AttackBox. يجب تنفيذ هذا الاختبار على عنوان Lab machine المخصص للغرفة فقط، مع تشغيل listener قبل رفع الملف:

```bash
rlwrap nc -lnvp 1337
```

يُرفع الملف باسم Python مثل `shell.py` عبر وظيفة صورة الملف الشخصي. جوهر الخلل ليس امتداد الملف وحده، بل أن التطبيق يعالج الملف المرفوع بطريقة تسمح بتنفيذه أو استيراده في سياق الخادم بدلاً من اعتباره صورة غير قابلة للتنفيذ.[2] [3]

### 5. تشغيل الحمولة واستلام shell عكسي

بعد رفع الملف، تُستدعى الوظيفة التي تعيد معالجة الصورة، مثل عرض الملف الشخصي أو عملية المعالجة الخلفية المرتبطة بالملفات المرفوعة. عند نجاح trigger، تصل جلسة إلى الـ listener. تُثبت هوية العملية ومستوى الصلاحيات داخل shell:

```bash
id
whoami
```

تظهر الجلسة بصلاحيات `root`، ما يعني أن التطبيق يعمل دون فصل صلاحيات مناسب. يؤدي ذلك إلى تحويل رفع ملف غير موثوق إلى تنفيذ أوامر على النظام المضيف.[2]

### 6. قراءة العلم

بعد التأكد من الجلسة، يُبحث عن ملف العلم في سياق التطبيق:

```bash
cat flag.txt
```

يعرض الملف العلم بصيغة `THM{...}`، وهو المطلوب في السؤال الوحيد للغرفة. لا حاجة إلى مهاجمة أي خدمة خارجية أو توسيع النطاق؛ يكفي استخدام نقطة الرفع ومسار التنفيذ داخل Lab machine المخصص.[2]

## الدروس الأمنية

توضح الغرفة أن التحقق من امتداد الملف أو اسمه وحده لا يكفي لحماية وظيفة الرفع. يجب السماح بقائمة امتدادات وأنواع MIME محددة، والتحقق من المحتوى فعلياً، وإعادة تسمية الملفات، وتخزينها خارج webroot ومسارات التنفيذ، ومنع أي عملية لاحقة من استيراد ملفات يسيطر عليها المستخدم.[3]

ينبغي كذلك تشغيل التطبيق بحساب خدمة محدود الصلاحيات وليس `root`. فحتى إذا تجاوز المهاجم ضوابط الرفع، يمنع مبدأ أقل الصلاحيات انتقال الخلل من تنفيذ كود في التطبيق إلى السيطرة الكاملة على النظام. كما يجب عزل مجلدات الرفع عن أي آلية plugin أو dynamic import أو template evaluation.

ومن منظور الاختبار، ينبغي فحص كل وظيفة ترفع أو تعالج الملفات بامتدادات متعددة، والتحقق من أن الملف يبقى بيانات غير قابلة للتنفيذ عند طلبه أو معالجته. كما يجب تسجيل محاولات رفع امتدادات غير متوقعة، ومراقبة الاتصالات الصادرة من عملية الويب، وإضافة اختبارات تمنع استدعاء ملفات المستخدم في سياق Python التنفيذي.
